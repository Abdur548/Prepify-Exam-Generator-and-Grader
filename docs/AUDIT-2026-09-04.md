# Audit — the frontend build and its backend seams

**2026-09-04.** Scope: everything added between `ccce3cf` and `5294f28` — the five
screens, the provenance card, the streaming endpoint, the ingest job, the chat
guard, the preflight gate, and the upload path they all sit on.

Every finding below was **reproduced against the code**, not inferred from
reading it. Where a claim rests on judgement rather than a run, it says so.

**Secrets: clean.** Scanned across all commits at push time — no key patterns
(`AIza…`, `AQ.…`, `sk-…`), no `.env` in the tree (`backend/.env` is gitignored),
no course material tracked, no `output/` or `dist/` artifacts. The only key

## Severity 1 — data loss and process death

### A1. Uploading two files with the same name silently keeps one

`_safe_upload_name` reduces every upload to its basename. Nothing then
distinguishes two files that share one.

```
input : ['week1/notes.pdf', 'week2/notes.pdf', 'notes.pdf']
output: ['notes.pdf', 'notes.pdf', 'notes.pdf']
distinct: 1 of 3 -> COLLISION
```

Each write overwrites the last. The student picked three decks; one is indexed.

It is worse than a lost file, because the UI actively confirms the loss did not
happen: `_save_uploads` returns the duplicated list, the upload screen lists
three rows, and then `_apply_ingest_event` keys file rows **by name** — so the
three rows merge into one as parsing starts, with no message. A student watching
that sees their file list shrink and has no reason to think anything was dropped
rather than deduplicated.

Introduced by the traversal fix (2026-09-04). The prior code was also broken here
— `source_dir / "week1/notes.pdf"` created a subdirectory that
`parse_directory`'s non-recursive `iterdir()` never scanned, so those files were
skipped silently too — but the fix changed *which* way it breaks without closing
it.

### A2. Uploads are buffered whole in memory, with no cap on size or count

```python
(dest_dir / name).write_bytes(await f.read())   # main.py:200
```

`_check_file_size` exists, but it runs in `parse_file` — **after** every byte has
been read into memory and written to disk. There is no limit on the number of
files, no limit on total bytes, and no streaming.

This lands on the one resource the system already cannot survive losing.
Preflight's `memory` check exists because BGE-M3 needs ~4 GB of committable
memory and below that **the OS kills the process with an access violation that no
handler can catch and no screen can report** — that is the documented reason the
gate was built. A ten-file upload at the per-file limit is 1 GB resident before
anything is validated. The upload path can therefore kill the process in exactly
the way the rest of the system is carefully arranged to prevent.

## Severity 2 — a screen that says something untrue

### B1. An ingest queued behind chat or generation reports "running", with no stage

`_ingest_job` sets `status="running"` and *then* calls `_ingest_under_lock`,
which takes a blocking acquire. While it waits, the job is reported as running
with `stage: null`.

The upload screen renders that as three pending stages, a climbing elapsed clock,
and no explanation — indistinguishable from a hung ingest. Chat can hold that
lock for ~40 s on a cold model load, and a generation for the better part of a
minute.

The exam stream solves exactly this with a `waiting` stage naming the holder
(`main.py:672`). The ingest job has no equivalent — `"waiting"` appears twice in
the file, both in the stream.

### B2. A stalled stream hangs the generating screen indefinitely

`useGenerationRun` has no timer of any kind (`0` occurrences of `setTimeout` or
`AbortSignal.timeout`), and the NDJSON protocol has no heartbeat.

A stream that **closes** without a terminal event is handled — that was fixed on
2026-09-03. A stream that stays open and stops sending is not: the stage rail
stays live, the clock keeps climbing, and nothing ever resolves. A student has no
signal to distinguish "still writing questions" from "gone".

### B3. Chat suggests questions about a course the student may not be taking

```ts
const SUGGESTIONS = [
  "What is an admissible heuristic?",
  "Explain alpha-beta pruning simply",
  "Where do my notes cover constraint satisfaction?",
];
```

Hardcoded to the AI corpus this was developed against. A student who uploaded
organic chemistry is offered three questions about search algorithms as the first
thing on the screen.

This is the same class of defect as the hardcoded blueprint presets fixed earlier
today: **the UI asserting facts about content it cannot know.** The course map
holds real topics; the empty state should draw on them or offer nothing.

### B4. The upload size limit is duplicated, not derived

`UploadScreen.tsx:34` hardcodes `100 * 1024 * 1024` with a comment pointing at
`config.MAX_FILE_SIZE_BYTES`, and the rejection message hardcodes "100 MB" again
at line 114. Three copies of one number, two of them in the client. Change the
config and the client rejects files the server would accept, or accepts files it
will not.

## Severity 3 — worth fixing, not urgent

### C1. `/api/internal/reset-disclosure` is live and unauthenticated

`API-CONTRACT.md` marks it "Test seam. **Not for the UI.**" It is nonetheless a
real POST route on the running server with no guard. Anything that can reach the
port can clear the consent gate.

Impact is small — it re-gates rather than un-gates, so it makes the system more
conservative, not less. But an unauthenticated state mutation labelled "not for
production" should not be reachable in production.

### C2. There is no authentication anywhere

By design: single user, `127.0.0.1`, one worker. Recorded because every finding
above is reachable by anything that can open that port, and A1/A2 are file-write
and memory-exhaustion primitives. The moment this binds to anything but
loopback, they change severity.

### C3. `_pipeline_holder` is written under the lock and read without it

A queued caller can read a label a moment stale. Documented at the definition as
copy-only and never a decision, which is correct — the worst case is a slightly
wrong sentence. Noted so it is not mistaken for a synchronisation primitive
later.

### C4. The provenance drag swallows text selection

`ProvenanceCard.onPointerDown` ignores presses on `button, a`, but not on text. A
student dragging across a question stem to select it starts the card gesture
instead. There is no way to select question text with a mouse.

### C5. `PaperActions` probes by fetching and cancelling

`/api/files` answers 405 to HEAD, so availability is checked with a GET whose
body is cancelled on arrival. For small files the body may already be in flight
before the cancel lands — a few hundred KB per visit to the Paper screen.
Correct, just not free.

## What this audit did NOT cover

- **The backend before this build.** The solver, the validation gates, the
  factuality instrument and the render path were not re-examined.
- **Anything under load or concurrency.** Every finding is from single-user
  reasoning and single-user runs. The pipeline lock has never been tested with
  genuinely concurrent callers.
- **The frontend under automated test.** There is no frontend test runner in this
  repo, so none of the eleven findings has a regression test, and none of the
  fixes below can get one without standing one up.
- **Accessibility beyond keyboard reachability.** No screen reader pass, no
  contrast audit. `--trace` at `#B8E62E` is still flagged as needing one in
  `UI-DESIGN.md` §8.3.
